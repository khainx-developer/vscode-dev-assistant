# AI Engineering Standard — Implementation Task Package Specification (ITPS)

**Version**: 1.0

This is the quality bar for how a single task from `04-ExecutionPlan/ExecutionPlan.md` (EPS §5)
is handed to the Developer. It is a standard, not a template — the fill-in template that
follows this structure is `ai-factory/templates/TaskPackage.md`. It governs the *shape* of a
Task Package; `ai-factory/gates/cis-standard.md` governs the Developer's *behavior* while
executing whatever package it's given — the two are complementary, not overlapping.

## Purpose
A Task Package is the smallest executable work unit for the Developer. **The Developer should
never receive the whole Execution Plan** — only one Task Package at a time, containing
everything needed to complete that one task and nothing about any other task. This is the
sharpest tool in the pipeline against implementation drift: a Developer that can't see the rest
of the plan can't reinterpret it, reorder it, or scope-creep into it.

Task Packages are generated by the Architect/Analyst role (the Planner) as the final step of
stage 04, immediately after ExecutionPlan.md's Approval Gate is confirmed — one file per Task
Specification block, expanded with the extra context (Background, Business Rules subset,
Constraints, Common Mistakes) a Developer working in isolation needs. They live in
`04-ExecutionPlan/tasks/TASK-00N.md` — Architect-owned and read-only to the Developer, same as
ExecutionPlan.md itself.

The Developer's job is **translation, not thinking**: turn a Task Package into code exactly as
specified. It does not reason about whether the approach is right, does not weigh alternatives,
does not decide what "probably" belongs in scope — those are Planner (Architect/Analyst)
decisions, already made upstream in BRS/SDS/TDS/EPS. If executing a task ever requires a
judgment call beyond the narrow list in §19 Developer Freedom, that is not execution — it is a
sign the package is incomplete, and it becomes a Blocking Condition, not something to reason
through.

## Core Principles
Every Task Package must be: Atomic, Self-contained, Deterministic, Verifiable, Independent,
Complete. The Developer should never need an additional architectural decision to use one.

**Code-level determinism.** "Translation, not thinking" only works if the package already contains
the answer. A package that says *what* to build but leaves the *how* of a non-trivial query,
algorithm, or helper to the Developer does not remove that decision — it hands it to the model,
which fills it with the most plausible, least-reviewed code. Spec out any non-trivial query,
algorithm, or data-shape decision at whatever level of specificity the project's own
`coding-standard.md` calls for — don't leave "make it work" as the instruction.
**The code spec is required, not optional** wherever `ai-factory/gates/code-spec-standard.md`
applies; a package missing it is incomplete, and the Developer's preflight blocks on it.

## AI Quality Gate
Self-check the Planner runs **before finalizing each Task Package** (not a user-facing
confirmation gate — this is a per-task generation check, run silently for every package):

1. Is the objective clear?
2. Are required files identified?
3. Are forbidden files identified?
4. Are dependencies completed (or clearly listed if not yet)?
5. Is the expected output measurable?
6. Can this task be completed independently?
7. Can completion be objectively verified?
8. Will the Developer need to guess? *(must be NO)*
9. If the task triggers `code-spec-standard.md`, is §9.1-§9.5 fully filled and does it pass that
   standard's Planner readiness gate (10 questions)? *(must be YES — otherwise N/A with reason)*

If any answer is NO (or #8 is YES), regenerate the package — don't ship an ambiguous one.

## Anti-Patterns
Unacceptable as a task Objective — a verb with no artifact named is not an instruction:

- "Implement feature."
- "Fix bug."
- "Refactor module."
- "Improve code."
- "Update repository."

Acceptable — names the exact artifact:

- "Add CreateAppointmentCommand."
- "Implement AppointmentValidator."
- "Add AppointmentCreated event."
- "Update AppointmentRepository to support optimistic concurrency."

The Developer should always know exactly what to implement without interpreting intent.

## Blocking Conditions
Stop implementation immediately — never continue by guessing — if: a business rule is missing,
an architecture conflict appears, an unexpected dependency turns up, a database conflict is
found, a security issue is identified, or the requirement is ambiguous. Report it (in
`05-Implementation/notes.md`, keyed by Task ID) rather than resolving it yourself.

## Definition of Done (per Task Package)
A Task Package is complete only when:

- [ ] Objective achieved
- [ ] Acceptance criteria satisfied
- [ ] Validation steps completed
- [ ] Tests passed
- [ ] Documentation updated (if the task called for it)
- [ ] No implementation drift detected (nothing outside Files To Create/Modify was touched)
- [ ] The task can be merged independently
- [ ] Preflight and self-review evidence recorded in `05-Implementation/notes.md` (when §9.1-§9.5 applied)
